1. Wprowadzenie i zakres

Emma Notify jest usługą integracyjną Tiemed, która odwzorowuje dane operacyjne z Airtable w PostgreSQL, wykrywa zdarzenia biznesowe, planuje i wysyła komunikację, a odbiorcom udostępnia bezpieczny portal spraw, urządzeń i dokumentów.

Odpowiedzialności systemu

  • jednokierunkowe pobieranie danych z Airtable — bez zapisu do źródła;
  • utrzymywanie lokalnego, znormalizowanego obrazu spraw, zadań, urządzeń, szpitali i kontaktów;
  • wykrywanie zmian i tworzenie idempotentnych zdarzeń komunikacyjnych;
  • rozstrzyganie odbiorcy, harmonogramowanie, budowa payloadu i wysyłka przez Resend;
  • generowanie podpisanych linków do portalu i rezygnacji z komunikacji;
  • udostępnianie portalu placówki, kontrolowanego odświeżania oraz prywatnych załączników;
  • rejestrowanie analityki pierwszej strony i diagnostyki całego pipeline’u.
Uwaga o aktualności README: początkowe zdanie README („nie wysyła wiadomości e-mail”, „brak frontendu”) opisuje wcześniejszy etap projektu. Aktualny kod zawiera produkcyjny sender Resend, portal HTML i panel analityczny. Niniejszy dokument opisuje stan implementacji, nie historyczny opis.

Granice systemu

Poza zakresem są: edycja Airtable, zarządzanie użytkownikami w klasycznym modelu login/hasło, ogólny CMS, trwałe publiczne URL-e do plików i automatyczne wykonywanie migracji przy starcie.

Topologia produkcyjna

Usługa API

Proces bezstanowy: node dist/api/index.js. Wymaga PostgreSQL, sekretu linków oraz — gdy włączone — storage i Basic Auth analityki. Renderuje HTML po stronie serwera i JSON dla dynamicznych widoków.

Usługa Worker

Długowieczny proces: node dist/worker/index.js. Utrzymuje heartbeat, wykonuje baseline i wiele chronionych flagami pętli pollingowych. Nie ma publicznego portu HTTP.

PostgreSQL

Wspólny stan koordynacji. Constraints i transakcje zapewniają idempotencję; lease’y ograniczają równoległą pracę. Migracje są osobnym krokiem wdrożenia.

Integracje zewnętrzne

Airtable REST (GET), Resend API i kompatybilny z S3 Railway Object Storage. Wszystkie sekrety przekazywane przez zmienne środowiskowe.

Główne decyzje architektoniczne

  • Airtable Record ID jako klucz techniczny — numery biznesowe mogą się powtarzać.
  • At-least-once polling + idempotencja — overlap checkpointu celowo może zwrócić rekord ponownie.
  • Rozdzielenie obserwacji od dostawy — zdarzenie, odbiorca, delivery i wysyłka mają osobne stany.
  • Snapshoty — event i send snapshot zachowują dane użyte do decyzji i wysyłki.
  • Fail closed — niepełny scope szpitala, nieprawidłowy token, opt-out lub niegotowy asset blokują bezpiecznie.

Cykl startowy workera

  1. Walidacja konfiguracji i utworzenie klientów.
  2. Upsert WorkerState(main), log kill switcha poczty.
  3. Cleanup historycznych delivery względem COMMUNICATION_SEND_NOT_BEFORE.
  4. Start heartbeat co 30 sekund.
  5. Baseline Airtable; naprawa scope szpitala; baseline komunikacji serwisowej; backfill reportedAt.
  6. Dopiero po powodzeniu baseline uruchamiane są pętle pollingowe. Przy błędzie baseline worker utrzymuje heartbeat, ale nie przechodzi do pollingu.

4.1 Synchronizacja danych

Baseline pobiera pełny zbiór. Incremental odejmuje AIRTABLE_SYNC_OVERLAP_SECONDS od ostatniego sukcesu i filtruje po polu „Last mod Emma”. Powtórzenia są oczekiwane. Stan zmienia się atomowo z checkpointem, a źródłowy snapshot ułatwia późniejszą diagnostykę.

4.2 Aktualny pipeline komunikacyjny

Observation
→
CommunicationEvent
→
Recipient resolution
→
Delivery planner
→
Resend
  1. Mapper tworzy obserwację scenariusza i deterministyczny fingerprint.
  2. CommunicationCursor porównuje sygnaturę i rewizję; duplikat nie tworzy nowego eventu.
  3. Resolver buduje odbiorcę klienta lub kontrolowany fallback Tiemed, zapisując status i bezpieczną diagnostykę.
  4. Planner tworzy delivery i scheduledFor: event-driven albo harmonogram 06:00; zbiorcze komunikaty napraw są planowane produkcyjnie na 06:00 i 14:00.
  5. Sender claimuje rekord, sprawdza kill switch, opt-out, datę aktywacji, aktualność stanu, pliki i dane szablonu.
  6. Powstają granty portalu i unsubscribe, snapshot wysyłki oraz idempotency key dostawcy. Wynik to SENT, retry albo terminalne FAILED/CANCELLED.

4.5 Portal refresh

Użytkownik z ważnym grantem wysyła żądanie; API tworzy unikalne aktywne PortalRefreshRequest i zwraca 202. Worker claimuje zadanie, odświeża wyłącznie autoryzowane rekordy spraw, urządzeń i zadań oraz synchronizuje ich załączniki. Klient odpytuje status. Refresh nie fabrykuje delivery ani nie wykonuje globalnego backfillu.

Mapowanie

Integracja używa przede wszystkim Field IDs z src/airtable/field-ids.ts, dzięki czemu zmiana etykiety pola nie psuje kontraktu. Załączniki są świadomie wydzielone z podstawowych list pól i pobierane tylko przez resolver assetów. Snapshot źródłowy jest przechowywany jako JSON dla audytu, ale tymczasowe URL-e Airtable nie są utrwalane.

Odporność

  • paginacja sekwencyjna; checkpoint dopiero po poprawnym przetworzeniu;
  • overlap domyślnie 120 s chroni granice timestampów;
  • reconcile ma cursor, liczniki i lease w SyncState;
  • portal refresh ogranicza zbiór do scope danego grantu;
  • błędy są logowane jako bezpieczne kategorie bez sekretów i surowych payloadów.

7. Model danych PostgreSQL

Schema dzieli się na pięć obszarów: lokalny cache źródła, komunikację, pliki, portal/analitykę oraz legacy digesty.

7.1 Cache źródłowy

TrackedCase i TrackedCaseDevice

Naprawa lub przegląd identyfikowany unikalnie przez parę (caseType, airtableRecordId). Zawiera dane biznesowe, bieżący status, pełny zestaw pól portalu naprawy/przeglądu, znaczniki czasu źródła, aktywność i snapshot. Relacja urządzeń jest many-to-many przez techniczne Airtable IDs.

TrackedTask

Cache zadania: numer, dzień, aktywność, status/complete, status i szablon Emma, szpital, wybrane kontakty, linkowane inspekcje/zlecenia i wykonawcy. airtableRecordId jest unikalny.

TrackedDevice

Rejestr urządzeń placówki: identyfikacja, lokalizacja, status techniczny i Emma, rok, uruchomienie, gwarancja, EPC, snapshot i aktywność.

TrackedHospital i HospitalPortalEntitlement

Szpital przechowuje nazwę, adres i snapshot. Entitlement steruje zakresem portalu: COMMUNICATION albo FULL, niezależnie dla sourceHospitalRecordId.

7.3 Pliki

StoredFile reprezentuje fizyczny plik i jego warianty; CaseAsset bieżące przypięcie do sprawy, a CommunicationAsset niezmienne przypięcie do konkretnego delivery. Statusy: PENDING, PROCESSING, READY, FAILED. Role: zdjęcie, protokół naprawy/diagnostyczny, oferta, dokument lub zdjęcie przeglądu.

7.4 Portal i analityka

PortalAccessGrant wiąże publicId, delivery, szpital, kontekst wejścia, TTL, revocation i liczniki otwarć. PortalRefreshRequest jest kolejką z lease i jednym activeKey. AnalyticsEvent zapisuje kliknięcie linku, potwierdzenie widoku, ekran lub upgrade wraz ze scope.

7.5 Legacy

CaseRecipient, CaseEvent, NotificationBuffer, BufferItem, Digest, DigestItem i AccessLink obsługują starszy mechanizm agregowanych digestów. Są ważne dla migracji i danych historycznych, choć aktywny incremental nie generuje nowych legacy notifications.

7.6 Koordynacja

SyncState przechowuje baseline, ostatni sukces, status, cursor, lease i liczniki dla encji. WorkerState(main) zawiera wersję, start, heartbeat, ostatni sync i znacznik cleanupu komunikacji.

Polityka usuwania: rekordy zależne eventu/delivery/grantu zwykle mają onDelete: Cascade; historyczny DigestItem → TrackedCase oraz asset relations używają Restrict, aby zapobiec utracie referencji audytowej lub fizycznego pliku.

8. Komunikacja e-mail

Tryby i kill switch

  • EMMA_MAIL_TEST_MODE=true: odbiorcą może być wyłącznie TEST_EMAIL, cron wspólny z EMMA_MAIL_TEST_CRON, włączona rozszerzona diagnostyka.
  • false: tryb produkcyjny; planner używa harmonogramu 0 6,14 * * * dla digestów napraw.
  • COMMUNICATION_EMAILS_ENABLED jest operacyjnym kill switchem. Legacy PRODUCTION_EMAILS_ENABLED nie steruje workerem.
  • COMMUNICATION_SEND_NOT_BEFORE wyznacza granicę aktywacji i zabezpiecza przed wysyłką historii.

Resolution odbiorcy

Resolver działa na eventach oczekujących, rozróżnia CLIENT i TIEMED_FALLBACK, normalizuje e-mail, zapisuje źródło oraz powód decyzji. Maksymalnie cztery próby korzystają z backoffu. Brak pewnego scope lub konflikt danych nie może doprowadzić do przypadkowej wysyłki.

Szablony i payload

Zmienne tekstowe są ograniczone do 2000 znaków. Szablony tabelaryczne mają 30 slotów; także widoczny limit e-maila wynosi 30 pozycji. Liczniki są normalizowane do liczb. CTA i unsubscribe są budowane jako bezpiecznie escapowany HTML. Dla napraw wspierany jest batch payload.

Retry i idempotencja

Delivery jest claimowane przejściem do SENDING, ma attemptCount, nextRetryAt, sendingStartedAt, provider message ID i ostatni błąd. deliveryKey, logicalDigestKey oraz klucz idempotency Resend chronią przed duplikacją na kolejnych warstwach.

9. Portal klienta

Portal jest generowany przez API jako samodzielny dokument HTML z nonce CSP, a dane szczegółowe pobiera z endpointów JSON. Dostęp nie opiera się na sesji użytkownika, lecz na podpisanym, wygasającym i odwoływalnym grancie związanym z konkretnym delivery i placówką.

Poziomy dostępu

COMMUNICATION

Zakres wynikający z komunikacji i jej kontekstu wejścia. Ogranicza sprawy/urządzenia do danych związanych z delivery.

FULL

Pełny widok danych placówki zgodnie z HospitalPortalEntitlement, nadal ograniczony do jednego sourceHospitalRecordId.

Paginacja i wyszukiwanie

Listy spraw oraz urządzeń stosują nieprzezroczyste kursory, limit konfigurowany przez PORTAL_PAGE_SIZE (maks. 100), filtrowanie i wyszukiwanie. Niepoprawny cursor daje kontrolowany błąd; API nie akceptuje dowolnego offsetu.

Analityka

Rejestrowane są: EMAIL_LINK_CLICK, PORTAL_VIEW_CONFIRMED, SCREEN_VIEW i UPGRADE_CLICK. Payload ma allowlistę pól, UUID sessionId i ograniczone formaty nazw ekranu/encji. Błąd zapisu kliknięcia nie blokuje otwarcia portalu.

Transformacje

  • obrazy: kontrola rozmiaru i liczby pikseli, wariant portal WebP (domyślnie do 1920 px, quality 82) i miniatura (400 px, quality 78);
  • dokumenty: przechowywane jako wariant dokumentu bez transformacji obrazu;
  • tymczasowy URL Airtable jest rozwiązywany tuż przed pobraniem i nigdy nie trafia do bazy;
  • obiekty są prywatne, a API zwraca redirect do signed URL ważnego domyślnie 300 s.

Odporność i diagnostyka

Proces ma claim, konfigurowalną współbieżność, cztery próby z backoffem i nextAttemptAt. Etapy logów: AIRTABLE_FETCH, ATTACHMENT_DOWNLOAD, IMAGE_TRANSFORM, STORAGE_UPLOAD, DATABASE_UPDATE, ACCESS_SCOPE, RETRY_SCHEDULED, RETRY_EXHAUSTED. Logi nie zawierają URL-i, nagłówków, credentiali ani zawartości.

Włączenie COMMUNICATION_ASSETS_ENABLED=true wymaga kompletu ustawień storage. Endpoint musi być credential-free HTTPS. Poprawny FORCE_PATH_STYLE zależy od konfiguracji bucketu.

12. Bezpieczeństwo

Tokeny

HMAC z sekretem min. 32 bajty, publicId oddzielony od sygnatury, TTL i revocation. Weryfikacja używa bezpiecznego porównania.

Izolacja tenantów

Każde zapytanie portalu jest ograniczane przez sourceHospitalRecordId, grant i poziom entitlement.

Przeglądarka

CSP z nonce, zakaz frame ancestors, bezpieczne nagłówki publicznych stron i brak trwałego cache danych chronionych.

Pliki

Prywatny bucket, autoryzacja przed podpisaniem, krótki TTL, restrykcyjne allowlisty pól i limity wejścia.

Ochrona danych i sekretów

  • diagnostyki CLI maskują e-maile i nie pokazują tokenów;
  • logi assetów nie utrwalają tymczasowych URL-i ani surowych wyjątków;
  • API nie potrzebuje sekretu Airtable — należy zachować separację usług;
  • analityka ops jest domyślnie wyłączona i wymaga Basic Auth;
  • body analityki ma limit 8 KB i ścisłą allowlistę;
  • URL bazowy i storage muszą być HTTPS bez osadzonych credentiali.

Rekomendowane kontrole produkcyjne

  • rotacja PAT Airtable, klucza Resend, storage i signing secret według procedury;
  • oddzielne sekrety per środowisko i minimalne uprawnienia;
  • TLS na wejściu Railway oraz brak bezpośredniej ekspozycji PostgreSQL;
  • alert na przestarzały heartbeat, serie FAILED, niekończące się PENDING_DATA i retry exhausted;
  • regularny test odtworzenia backupu bazy.

13. Budowanie i wdrożenie

Wymagania

Node.js ≥ 20.19, PostgreSQL, npm, skonfigurowana baza Airtable. Opcjonalnie Resend i S3-compatible storage.

npm ci
npm run prisma:validate
npm run build
npm test
npm run db:migrate:deploy

npm run build czyści dist, generuje Prisma Client i kompiluje TypeScript ES2022/NodeNext. Testy nie są częścią builda i powinny być osobnym gate’em.

Railway — kolejność

  1. Utwórz PostgreSQL i wykonaj backup przed zmianami schema.
  2. Utwórz osobne usługi API i Worker z tego samego artefaktu.
  3. Wykonaj prisma migrate deploy jako pre-deploy lub jednorazowy job. Procesy aplikacji nie migrują bazy.
  4. Wdróż z COMMUNICATION_EMAILS_ENABLED=false.
  5. Uruchom API: npm run start:api; Worker: npm run start:worker.
  6. Zweryfikuj health, heartbeat, baseline, cykle synchronizacji i diagnostykę komunikacji.
  7. Dopiero po audycie kolejek ustaw granicę aktywacji i włącz wysyłkę.
Wdrożenie zmian komunikacji: runbook wymaga stop-the-world — zatrzymania wszystkich starych workerów przed migracją, zachowania danych diagnostycznych i niewznawiania historycznych eventów. Rollback aplikacji nie oznacza rollbacku addytywnej schema.

Graceful shutdown

Worker obsługuje SIGTERM/SIGINT, blokuje nowe prace, czyści timery i rozłącza Prisma. API po sygnale zamyka listener, rozłącza bazę i kończy proces. Platforma powinna zapewnić wystarczający termination grace period.

Recovery plików

Po usunięciu przyczyny można wskazać maksymalnie 25 terminalnych StoredFile przez ASSET_RETRY_STORED_FILE_IDS i potwierdzić ASSET_RETRY_APPROVED=true. Nie wolno masowo resetować wszystkich failure.

Reconcile przeglądów

Pierwszy przebieg zawsze ręczny z confirmation tokenem. Dopiero po sukcesie można włączyć harmonogram. Job wznawia się z zatwierdzonego cursoru i nie generuje komunikacji.

15. Strategia testów

Projekt używa Vitest. Testy jednostkowe i integracyjne z atrapami znajdują się obok modułów i obejmują konfigurację, mapowanie Airtable, synchronizację, idempotencję, retry, scope portalu, layout, tokeny, e-mail i pliki.

Najważniejsze klasy testów

  • kontrakty Table/Field IDs i mappery;
  • baseline/incremental/reconcile;
  • event, recipient, delivery, cleanup;
  • template payload i sender Resend;
  • portal policy, refresh i view modele;
  • asset sync i migracja.

Smoke tests

Katalog SmokeTests zawiera skrypty PowerShell/CMD do kontroli środowiska i backfillu duration. Należy traktować je jako narzędzia operacyjne wymagające wskazania środowiska, nie automatyczny test CI.

Weryfikacja release

  1. npm run prisma:validate i npm run build.
  2. npm test bez pomijania testów.
  3. Test migracji na kopii aktualnej bazy.
  4. Start obu procesów z wysyłką wyłączoną.
  5. Health + heartbeat + jeden cykl każdego pollera.
  6. Test portalu i pliku w scope testowej placówki.
  7. Test-mode wysyłki wyłącznie na TEST_EMAIL.
  8. Audyt kolejki przed produkcyjnym enable.

Niezmienniki krytyczne

  • Airtable pozostaje read-only.
  • Record ID, nie numer biznesowy, jest kluczem integracji.
  • Żadna wysyłka bez jednoznacznego scope szpitala i kill switcha.
  • Brak globalnego replay/resetu historycznych eventów podczas deployu.
  • Tymczasowe URL-e i sekrety nie są utrwalane ani logowane.
  • Migracje poprzedzają uruchomienie nowego kodu.
